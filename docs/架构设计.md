# 架构设计

## 一、为什么要分三层

评测项目最容易踩的坑，是把「被评测的系统」和「评测逻辑」写在一起：工具自己做了路径校验，
防御关掉也测不出脆弱面，最后所有指标都是自证清白。

所以这里按职责硬切三层：

| 层 | 目录 | 职责 | 不该做的事 |
| --- | --- | --- | --- |
| 能力层 | `app/agent/tools.py` | 提供读文件、查库、发消息、HTTP 四个工具 | 不做任何权限/参数/内容判断 |
| 边界层 | `app/defense/layers.py` | 五层防御，拦截与改写都在这里 | 不关心用的是哪个模型 |
| 度量层 | `app/runner/*` + `app/judge/*` | 用例、执行、判定、聚合、报告 | 不修改被测系统行为 |

能力层仍保留两条实现安全：文件访问限制在项目目录内、HTTP 只做模拟不发真实请求。
它们和「被测的防御」无关，是为了让靶场本身不会真的造成危害。

## 二、一次运行的时序

```
runner.evaluate
  └─ 每个配置：DefenseStack(policy, overrides)
       └─ 每条用例：engine.run_case
            ├─ tools.reset_session()         隔离 outbox
            ├─ LangGraph: decide ──► act ──► 条件边
            │     decide  组装 view（含 ① 的改写）→ provider.decide()
            │     act     防御栈 before_call → 工具 → post_tool 包裹
            └─ RunResult（steps / answer / outbox / blocks / masked）
  └─ judge.evaluate（规则断言）→ 逐条 success
  └─ metrics.summarize → 分配置 / 分类型 / 逐层边际
  └─ 写 bench.md + summary.json + data.js + runs.db
```

多轮用例把 `turns` 逐条喂进同一会话：`turn_index` 递增、`step` 归零、`sent_targets` 清空，
其余状态（observations / executed）保留——这样「跨轮累积」的攻击才测得出来。

## 三、五层防御的接口设计

每层只实现需要的钩子，新增一层不改调用方：

```python
class Layer:
    def pre_model(self, view) -> None: ...          # 影响模型看到什么（① 用）
    def before_call(self, tool, args, ctx):         # 拦截 / 改写参数
        return None, args
    def post_tool(self, content) -> (str, bool):    # 处理工具返回值（① 包裹）
        return content, False
```

`DefenseStack.before_call` 依序调用，第一个 block 即返回，并记录 `{layer, tool, reason}`——
这份记录就是「哪一层拦住了什么」的一手证据，看板与报告都直接用它。

## 四、模型可插拔

`app/llm/` 下三个实现共用 `decide(view) -> Decision`：

| provider | 用途 | 是否联网 |
| --- | --- | --- |
| `scripted` | 确定性模拟 7B 级模型的失效方式 | 否 |
| `ollama` | 本地模型（qwen2.5:7b 等） | 本地 |
| `deepseek` | OpenAI 兼容接口 | 是 |

被测系统的「模型有多听话」与「防御有多有效」是两件事。scripted 把前者固定住，
才能让配置之间的差值只反映后者；接真模型后，同一套用例直接读出真实 ASR。

## 五、为什么没有让工具自己打日志

轨迹由 `act` 节点统一记录（工具名、参数、返回、是否被拦截、包裹标记）。
如果每个工具自己写日志，格式会漂移、拦截事件会漏记，判定逻辑就得跟着各工具改。
一处记录，判定与报告都只认这一份结构。
